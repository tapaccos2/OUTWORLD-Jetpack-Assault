# Scout executable follow-up 18: callback table construction (REPORT(8))

Executable SHA-256: `484c7dc19a6f45e81af6a85e617761e01ec64ea784b17c45f8274fccf8f6a4c3`

This report is the broad `OUTWARS SCOUT EXECUTABLE FOLLOW-UP`, not the focused transform-tail output. It still provides a useful partial view of the callback at `0x4DFCE4`, but the callback disassembly ends at `0x4DFF7C`, before its full control flow and tail.

## What the visible callback body establishes

The DPC parser calls `0x4DFCE4` with `0x420B00` as the handler entry. At callback entry, the routine saves incoming EDX and EBX, reads a global table pointer at `0x12D6C74`, and reads its count at `0x12D6C78`.

When the table pointer is non-null, the visible code writes a new 24-byte entry at the current table position:

- offset `+0`: incoming EAX;
- offset `+4`: zero;
- offsets `+8`, `+0xC`, `+0x10`: three DWORDs copied from a local snapshot;
- offset `+0x14`: incoming EDX.

It increments the global count and copies the preceding 24-byte entry into local working storage when one exists. This confirms that the callback maintains a compact, 24-byte-stride table of parser/handler state. It does **not** yet establish that this is the runtime Scout part-object table or that its entries are transforms.

The visible continuation examines the record pointer held in the table entry, reads its 16-bit field at `+2`, and follows additional record fields at `+0x10` and `+0x14`. It also writes six DWORDs into 24-byte-stride entries based at `0x12D6C74`. The excerpt stops mid-instruction at `0x4DFF7C`, so the full entry layout, branch conditions, and final effects cannot be safely inferred.

## Runtime object table remains a separate structure

The disassembly around `0x422332–0x422440` shows a distinct runtime-object registration mechanism:

- a pointer array starts at `0x647538`, with its count at `0x647534`;
- `0x422332` scans that array and compares each pointed record's WORD at `+2` with the current identifier;
- on a match, it stores the matching record pointer at runtime-object offset `+0x160`;
- `0x422400` adds a record pointer to the array, subject to a 16-entry limit and duplicate-ID check.

This gives a concrete record-ID association mechanism, but the callback's table at `0x12D6C74` and the runtime-object pointer array at `0x647538` must not be conflated. The report does not show the missing call or data flow that would connect them to Scout's eight mesh objects.
